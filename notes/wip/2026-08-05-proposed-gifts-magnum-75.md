item. Open gifts belong in the Museum Wave, where the images, argument,
countercase, discussion, TDH votes, and outcome can remain together.

2. one image-led part for each work;
3. a final synthesis containing the case, countercase, rights and technical

threshold, its status becomes **closed without selection** inside the Wave's

or collection holdings. If it is selected, the proposal becomes an intake
source for the later accession package and public accession scholarship.

Full artist, project, and object scholarship is deferred until accession. The
Wave dossier must nevertheless be accurate, visually useful, and sufficient
for an informed vote.

## Backend compatibility audit

The proposed 25,000-character part limit and 50,000-character Storm limit are
not yet safe to release. The audit used exact `6529seize-backend` main
`972d860d20dd512f4e039ab07350037e332e83be`.

- `POST /api/drops` is the only path with an aggregate content check. It
  accepts exactly 32,768 JavaScript UTF-16 code units and rejects anything
  larger. The seven-part Magnum manuscript contains 35,577 code units, so the
  current route rejects it by 2,809 units.
- The shared Joi part schema has no content maximum and no aggregate maximum.
  Exact executable probes accepted a 25,001-unit part and 50,001-unit totals
  through create, update, and Wave-description schemas. Update and
  Wave-description creation therefore bypass the route-only 32,768 check.
- OpenAPI declares 25,000 characters per part, but runtime validation does not
  enforce that declaration. No existing backend test covers either proposed
  boundary.
- `drops_parts.content` is MySQL `TEXT` under `utf8mb4`. A disposable strict
  MySQL 8.3 probe accepted 25,000 ASCII characters but rejected 25,000
  three-byte and four-byte characters. An honest 25,000-character contract
  therefore requires a wider column such as `MEDIUMTEXT`, not only Joi and
  route changes. Every current Magnum part is individually safe in `TEXT`;
  its largest part is 13,377 code units and 13,407 UTF-8 bytes.
- Every successful create or update serializes the full `ApiDrop` into one
  API Gateway `DROP_UPDATE` WebSocket send. A deliberately minimal message
  containing the seven Magnum parts is already 36,652 UTF-8 bytes, 3,884
  bytes above API Gateway's 32-KiB frame ceiling. Normal author, Wave, media,
  attachment, quote, and reply data only increase it. The current sender does
  not split or replace oversize messages, and it logs non-stale send failures
  without failing the HTTP request. Persistence can therefore succeed while
  connected clients silently miss the realtime update.
- HTTP JSON transport is not the constraint: Express accepts 5 MB. Signature
  hashing covers the complete canonical request and has no relevant size
  ceiling. Notification queues carry identifiers rather than the complete
  Storm. A Storm that invokes `@help6529` is a secondary edge case because the
  help-bot interaction also stores concatenated content in a `TEXT` column;
  this proposal does not invoke the bot.

Release-safe implementation must therefore be coordinated across backend and
frontend. The backend should use one shared validator for create, update, and
Wave-description paths; enforce 25,000 per part and 50,000 total at exact
inclusive boundaries; widen part storage for arbitrary Unicode; and select a
compact realtime invalidation/refetch event whenever the complete serialized
drop would exceed a conservative frame budget. The frontend must understand
that backward-compatible compact event before the backend can emit it. Tests
must include exact boundary, Unicode storage, Magnum-fixture, oversize
WebSocket, and create/update/Wave-description parity cases.

Focused baseline verification passed 44 tests across the drop schemas,
WebSocket message/notifier, and Wave routes after installing both dependency
layers declared by the repository. Frontend PR
[`#3630`](https://github.com/6529-Collections/6529seize-frontend/pull/3630)
is green at exact head `de72e2689cf03529fac3454cfef936359eff4d3a`, but it must not merge or deploy
as a standalone change. No backend source, database, deployment, or live Wave
was mutated during this audit.

## Owner-selected safe limit contract

The owner resolved the storage tradeoff on 2026-08-05. The release will retain
the existing MySQL `TEXT` column and enforce all three limits at the API
boundary: no part may exceed 25,000 JavaScript UTF-16 code units; no part may
exceed 65,535 UTF-8 bytes; and the sum of all part content may not exceed
50,000 UTF-16 code units. Exact boundaries are valid. This dual per-part rule
admits the complete Magnum manuscript while preventing a payload that fits the
character count but cannot fit the current byte-limited storage column.

The earlier audit conclusion that an arbitrary-Unicode 25,000-character
contract would require wider storage remains technically true, but it is not
the selected product contract and no database or entity type will change in
this release. Shared backend validation, OpenAPI, frontend preflight, and
boundary tests must express the selected three-limit contract consistently.
Frontend compact-event compatibility must reach production before the backend
can substitute `DROP_UPDATE_REF` for a serialized per-recipient WebSocket
message above the 28-KiB application ceiling. The backend limit deployment must
then precede the public 50,000-unit composer deployment.
